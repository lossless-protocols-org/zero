This is everything outside `src/` that ships in the app or builds it: where it lives, who calls it, how it is tested, and what to check when React Native moves. The audit behind this layout is `references/audit/2026-11-08-principal-engineer-audit.md`, §6 and §12.3.

## Rules

- **One spec per platform reach.** A method only one platform has goes in that platform's spec, which is `null` on the other. Don't add a method that silently does nothing. `__tests__/contract/nativeModules.test.ts` fails when a spec method is missing on a platform that provides the module, or when a module appears where it should be absent.
- **`src/native` has one gateway per module and no other importer:** `features/widgets/bridge.ts` for the widget modules, `pro/billing.ts` for the store, `pro/reminders.ts` for reminders (P9), `data/backup/vault.ts` for the encrypted backup (P10) and `pro/reportPdf.ts` for PDF reports (P12).
- **The widget never opens the database.** It reads the snapshot the app writes (`writeSnapshot`). With amounts hidden, the snapshot holds no amount at all, and `WidgetRendererBindTest` asserts that no size of the widget shows a digit.
- **Anything parsed in two languages has one fixture both read** (`contracts/`). Version literals (`WIDGET_SNAPSHOT_VERSION`, `WidgetSnapshot.VERSION`, `WidgetSnapshot.version`) are pinned to the fixture on all three sides.
- **Generated means generated.** Run `node scripts/widget-assets.mjs` after changing a locale's `widget.*` / `intents.*` keys or `contracts/widget-assets.json`. `--check` fails CI when it is stale. Its outputs:
  - Android: `widget_strings.xml` per locale, `widget_colors.xml` (light, dark, Android 12+ dynamic) and `widget_preview_strings.xml`;
  - iOS: `ZeroShared/Localizable.xcstrings`, and the regions marked `// BEGIN Generated … // END generated` in `ZeroShared/ZeroCards.swift` (`ZeroColors`) and `ZeroWidget/ThisMonthProvider.swift` (the gallery sample).
- **Roles that mirror an app token equal it.** `__tests__/contract/widgetAssets.test.ts` pins them to `ThemeContext`.
- **A native module that reaches outside the app has three parts, from its first commit** (3.0): the spec in `src/native/specs/`; a JavaScript fake with the same surface, so every rule above it is tested without a device; and a fixture in `contracts/` of scenarios and expected results that the Kotlin and the Swift tests both read, so the two platforms cannot answer the same situation differently. The native side reports facts and decides nothing: what the facts mean is one TypeScript function, tested once.
- **Store code lives in the `play` flavour only** (below). Nothing under `android/app/src/main` or `src/foss` may import a Google Play library.

## Decisions (and why)

- **The shared Swift is a member of both targets, and also a package for its tests.** Linking the package into the app would fail on three counts:
  - **Deployment target:** the app supports iOS 15.1 (RN 0.88's floor) while the package needs iOS 17.
  - **Siri metadata:** App Intents need target membership for it unless both sides adopt `AppIntentsPackage`.
  - **Strings:** the shared strings would move from the main bundle to the package bundle.

  Membership in two targets is the Apple template's way to share code between an app and an extension. The real risk of two compilations is drift, so `__tests__/arch/sharedSwiftSources.test.ts` keeps `Package.swift`'s `sources` and both targets' compile lists identical. Revisit this when the app's floor reaches iOS 17.

- **The TurboModules stay in the app, not in `modules/<unit>` libraries** (the audit's §12.3 sketch). A library cannot depend on the app, and the bridge calls the app's widget and quick-add code. Extracting them would mean injecting those as interfaces, which is a cost with no user. The `bridge/` package and the split specs give the separation without it.
- **A QA build on both platforms:**
  - Android `qa` build type: release settings, id `com.anotherwhy.zero.qa`, name "zero QA", debug-signed (`./gradlew assemblePlayQa`). The quick-add task affinity follows the installed id (`${applicationId}`). The static shortcuts need a literal `targetPackage` (the launcher does not resolve a resource there), so the QA build has its own `src/qa/res/xml/shortcuts.xml`; `__tests__/scripts/shortcuts.test.ts` pins each copy to its build's id.
  - iOS "zero QA" (`com.anotherwhy.zeroqa`) through `ZERO_BUNDLE_ID` / `ZERO_DISPLAY_NAME`.
  - Never install a test build over the owner's store install.
- **Two Android flavours, `play` and `foss`** (dimension `store`, 3.0 plan P2). `play` is the store build and the only one that will link Google Play Billing (`android/app/src/play`); `foss` is the same app without it (`android/app/src/foss`). Until billing lands the two are identical, and the merged manifests are byte-equal.
  - Every Gradle task names its flavour: `assemblePlayRelease`, `bundlePlayRelease`, `assemblePlayQa`, `testPlayDebugUnitTest`, `lintPlayDebug`, and the same with `Foss`. The package scripts (`bun run android`, `android:release`, `android:release:apk`) build `play`; `bun run test:android` runs both.
  - Outputs carry it too: `outputs/apk/play/release/app-play-release.apk`, `outputs/bundle/playRelease/app-play-release.aab`, `outputs/mapping/playRelease/mapping.txt`.
  - CI builds both release APKs and checks each against its own permission allow list (`scripts/check-no-read.mjs --flavour <play|foss> --apk …`). `foss`'s list never grows.
  - Both use the same application id today. A `foss` build that is ever distributed needs its own id and signing key first.
- **Hermes only.** The template's JavaScriptCore fallback (a floating `jsc-android`) is gone. Turning Hermes off is a build error.
- **The midnight alarm is re-armed at every app start** (`ZeroWidgetProvider.rearmMidnight`), because alarms do not survive a reboot and not every launcher sends `APPWIDGET_UPDATE` at boot. No boot receiver is used: that would need `RECEIVE_BOOT_COMPLETED`, which the no-read allow list does not grant.
- **Things that stay as they are, and why:**
  - **Rendering on the provider's main thread.** It takes milliseconds. Move to `goAsync()` only if the layouts grow.
  - **The catch-up publish each time the quick-add sheet opens.** It comes from the second `ReactActivity` flipping `AppState`, and `WidgetStore.write`'s dedupe makes it cost nothing visible.
  - **iOS `enqueue`'s three `UserDefaults` writes under the lock.** They are not atomic across keys, but the next snapshot write repairs a partial one.

- **Long-press the icon: one menu on both platforms.** Android's launcher shortcuts (`quickadd/LauncherShortcuts.kt`) and iOS's Home Screen quick actions (`WidgetSnapshot.quickActions()`, shared and tested in `ZeroShared`; installed by `ZeroQuickActions` in the app target) come from the same snapshot fields (`quick`, `last`): Add expense, Money in, "Add again" (the sheet filled in) and the top category, or the two top categories with no last expense or with amounts hidden. iOS taps open `zero://quick?…&amount=…&title=…` (validated in `src/navigation/linking.ts`). In a scene app `RCTLinkingManager.application(_:open:options:)` forwards nothing, so a warm tap re-opens the app's own URL (into `scene(_:openURLContexts:)`), and a cold one hands the URL to React Native as its launch URL.
- **No Android voice entry in 2.8 (decided 2026-11-09).** App Actions (`shortcuts.xml` capabilities) no longer reach Gemini, which replaced Assistant on phones. The successor, AppFunctions (`androidx.appfunctions`, 1.0.0-rc01; Android 16+), is a new dependency in a release candidate with Gemini access just out of preview, and an AppFunction hands zero's data to an agent that runs in Google's cloud, against "nothing leaves this device". Revisit for 3.x as a product decision (the owner's), with on-device-only functions if the platform allows.

- **The App Store code is tested inside a host app, not a Swift package** (3.0 plan P4). In a bare package test bundle `SKTestSession` offers no products and every purchase is "not entitled"; the test store needs a real app around the tests. Hosting them in zero itself would build React Native for a Swift unit test, so `ios/ZeroBilling/ZeroBillingHost.xcodeproj` compiles the same three Swift files the app does, at the app's deployment target, with complete concurrency checking. The project is committed and is regenerated by `scripts/billing-host-project.rb` only when a Swift file is added or removed. `__tests__/arch/billingSwiftSources.test.ts` fails if the app and the host stop compiling the same files.
- **On iOS, "owned" is what `Transaction.currentEntitlements` says, and nothing else.** A transaction that only `Transaction.latest(for:)` knows (refunded, expired, superseded) is reported as ended, never as owned. Unverified transactions are passed on marked `verified: false`, and the app's reducer neither grants nor ends Pro on them. Three things are never read as an ending (law L3: Pro ends only on a positive answer). A store holding no transaction for any product answers "cannot say" (`noTransactions`): that is every free user, and also a buyer's restored phone before it has reached the App Store, and on this store a real ending always leaves a transaction (a refund carries its revocation date, a lapse its expiry). A product whose facts contradict each other (a transaction not taken back, yet not listed as owned; the two reads are not made at one instant) is passed on marked `verified: false`, as is a subscription in a renewal state this build does not know and that is not listed as owned: the app neither grants nor ends Pro on such a record, and the other products in the answer still count. The cost, accepted: Pro stays on a phone whose Apple Account is signed out or switched, until the store holds a transaction again. `AppStore.sync()` runs only behind Restore, because it asks for the Apple account password.
- **What the local test store cannot show is left to the sandbox walk** (`docs/RELEASE_QA.md`, "The store on iOS"): a declined Ask to Buy (Xcode 27.2's test store lists it in `currentEntitlements` as if it had completed), the signed original-install version (`AppTransaction` reads "1.0" outside production), and real renewal timing.

- **Google Play Billing ships without Google's usage uploader, so the `play` build asks for no network permission** (3.0 plan P5, spike S1). The billing library itself declares one permission, `com.android.vending.BILLING`, and talks to the Play Store app over IPC. `INTERNET` and `ACCESS_NETWORK_STATE` come only from `transport-backend-cct` and `transport-runtime`, which upload the library's own usage statistics from inside the app; `android/app/build.gradle` excludes both, and `proguard-rules.pro` tells R8 the three classes the library still refers to are absent on purpose. On a Moto g84 (Android 15, library 9.1.0, minified build) the library logs "Skipping logging since initialization failed", connects, and answers both purchase queries and the product query. Removing the permissions but keeping the uploader also works, and leaves an upload job that can never succeed; that is why it was not chosen. **This is not a configuration Google supports.** Bumping the library version means: read its POM for new dependencies, rebuild, run `node scripts/check-no-read.mjs --flavour play --apk …` (it fails if a network permission or an uploader class is back), and repeat the device check in `docs/RELEASE_QA.md`. Not yet proved, for want of products in Play Console: a purchase, an acknowledgement, and a two-day soak (spike part 2).
- **Play's client is asked to connect before every request, not to reconnect by itself.** With `enableAutoServiceReconnection()` on, the first query after every set-up logged "already in the process of connecting" and a failed reconnection, and answered about a second late (same phone, same library). `GooglePlayStore.connect` does the job plainly, with a ten-second limit so no call can wait for ever; a service lost between connecting and asking is one failed request, which the app reads as "cannot say".
- **On Google Play, "no longer returned" is the answer; on the App Store it is not.** Play's client has no record of a refund or an expiry: the purchase simply stops coming back, so an empty answer from two successful queries is an answer and ends Pro. Every failure, of the connection or of either query, is "cannot say", and half an answer is never read as all of it. Play reports no end date and cannot tell a trial or a grace period from an ordinary active subscription, so nothing in the app may depend on either there. A paused or on-hold subscription is asked for explicitly (`includeSuspendedSubscriptions`) and reads `onHold`.
- **A purchase is acknowledged the moment it is seen, verified and paid**: in the listener and on every query, because Play refunds one left unacknowledged for three days. Never a pending one, never one whose signature fails. A build with no licence key cannot verify, so it sells nothing and answers "cannot say (noLicenceKey)"; that is the state of the tree until the owner pastes the key from Play Console into `PlayCatalogue.LICENCE_KEY` (and deletes the test that pins it empty).
- **The QA build type is declared after `release`.** `initWith release` copies what `release` holds at that point; declared first, as it was until 3.0, QA was copied before R8 was switched on and was never the minified code a user runs.

## Upgrading React Native: checklist

The app touches template internals in five places. Diff each against the new template (react-native-community/rn-diff-purge):

1. `MainApplication.kt`: `getDefaultReactHost(packageList = …)` plus `add(ZeroBridgePackage())`, and `loadReactNative(this)`.
2. `MainActivity.kt` and `quickadd/QuickAddActivity.kt`: a second `ReactActivity` (component `zeroQuickAdd`, registered in `index.js` on Android only) on the same `ReactHost`. The template has no second root, so check that `ReactActivityDelegate`'s constructor and `getMainComponentName` still hold.
3. `SceneDelegate.swift`: it subclasses `RCTDefaultReactNativeFactoryDelegate` (template shape since RN 0.80). The bridges no longer import `zero-Swift.h`, so a move of that header no longer breaks them.
4. The codegen config in `package.json` (`codegenConfig`: `jsSrcsDir`, `javaPackageName`, `ios.modulesProvider`): after a spec change, run `pod install` (iOS regenerates `ZeroSpecs`); Gradle regenerates on build.
5. `patches/@nozbe%2Fwatermelondb@0.28.0.patch`: re-run `bun install`. A patch that no longer applies fails the install. Then run the SQLite suites and the device checklist.

Also:

- **`gradle.properties`:** `android.builtInKotlin=false` and `android.newDsl=false` are the RN 0.88 template's opt-outs from AGP 9 behaviour, and AGP 10 removes them. Drop them when the template does.
- **Then run everything:**
  - `bun run check`, `bun run test:android`, `bun run test:ios` and `node scripts/widget-assets.mjs --check`;
  - a release build on the Moto, using the device checklist in `docs/RELEASE_QA.md`.
